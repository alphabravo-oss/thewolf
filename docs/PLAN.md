## 1. How to execute and maintain this plan

- An unchecked task is unfinished **or not yet verified against its acceptance criteria**. Existing code is a starting point, not proof of completion. Inspect it before adding anything.
- Check a task only after its stated implementation/documentation/check is complete. Append the date, runnable command or durable evidence, and any limitation on that same task or in §18. Implementation, deployment, and production qualification have separate tasks.
- Work on the earliest unblocked task in the current milestone. Record a concrete blocker and continue independent work; do not silently waive the blocked criterion.
- Keep task IDs stable. Add newly discovered defects under the responsible workstream, with reproduction and acceptance. Mark superseded choices explicitly; do not delete unfulfilled requirements to make the checklist green.
- Follow `AGENTS.md`: trace callers; reuse existing services/components; fix shared causes; avoid new dependencies and speculative abstractions. Non-trivial changes leave a runnable regression check.
- Deliver small reviewable changes. Do not combine license changes, schema rewrites, UI redesign, scanner updates, and isolation migration into one implementation PR. Preserve the pre-existing working tree; do not reset or silently stage unrelated work.
- Update this file in the same change as completed work. Release tasks require the exact source revision, artifact digest, deployment, date, command, outcome, and rollback evidence. Historical `/tmp` logs alone are not durable release evidence.
